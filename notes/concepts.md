# SQL 개념 정리 노트

프로그래머스 SQL 고득점 Kit을 풀면서 배운 개념을 순서대로 정리한 복습 노트입니다.

## 1주차 기초 — SELECT / WHERE / ORDER BY

| 문법 | 의미 | 주의사항 |
| --- | --- | --- |
| `SELECT 열 FROM 테이블` | 지정한 열만 조회 | `*`는 모든 열 |
| `WHERE 조건` | 조건에 맞는 행만 필터링 | 텍스트 비교는 작은따옴표 `'...'` 필수 |
| `ORDER BY 열 ASC/DESC` | 정렬 (ASC가 기본값) | `DESC`는 내림차순 |
| `=` / `!=` 또는 `<>` | 같다 / 같지 않다 | |

## 집계함수와 GROUP BY

| 함수 | 의미 |
| --- | --- |
| `COUNT(*)` | 행 개수 |
| `COUNT(DISTINCT 열)` | 중복 제외한 개수 |
| `SUM(열)` | 합계 |
| `MAX(열)` / `MIN(열)` | 최대값 / 최소값 |
| `AVG(열)` | 평균 |
| `AS 별명` | 결과 열에 임시 이름 붙이기 |

**GROUP BY의 핵심**: 여러 행을 같은 값 기준으로 세로로 묶어서 집계(합계/평균/개수 등)하는 것. GROUP BY로 묶은 다음에는 SELECT에도 집계함수와 GROUP BY 기준 열만 써야 안전하다 — 원본 값 열은 어느 행의 값이 나올지 보장되지 않는다.

## 조건 다루기 — LIKE / OR / BETWEEN

| 문법 | 의미 |
| --- | --- |
| `WHERE 열 LIKE '%텍스트%'` | 해당 열에 특정 문자열이 포함된 행만 (중간 일치) |
| `조건A OR 조건B` | 둘 중 하나만 만족해도 통과 |
| `열 BETWEEN A AND B` | A이상 B이하 범위 (날짜에도 쓰임) |

## JOIN

**개념**: 서로 다른 두 테이블을 공통 열(key)로 연결해서 하나의 테이블처럼 합치는 것.

**JOIN vs GROUP BY (헷갈리기 쉽지만 다름)**

| | 방향 | 하는 일 |
| --- | --- | --- |
| JOIN | 옆으로(가로) | 두 테이블의 열을 한 줄에 합침. 행 개수는 줄어들지 않음 |
| GROUP BY | 아래로(세로) | 여러 행을 한 줄로 뭉쳐 집계. 행 개수가 줄어듦 |

JOIN만으로 부족한 정보를 가져올 때(예: 저자ID만 있는 책 테이블에 저자명 붙이기) 쓰고, 집계(합계·평균 등)가 필요할 때만 GROUP BY를 추가로 붙인다.

**INNER JOIN vs LEFT JOIN**

- INNER JOIN: 양쪽 테이블에 둘 다 있는 행만 남김
- LEFT JOIN: 왼쪽 테이블의 행은 전부 유지하고, 오른쪽에 매칭이 없으면 NULL로 채움 → `WHERE 오른쪽.열 IS NULL`로 "매칭 안 된 데이터"를 찾아낼 수 있음

**외래키(Foreign Key)**: 한 테이블의 열이 다른 테이블의 기본키(Primary Key)를 가리키는 값. 두 테이블이 어떤 열로 연결되는지 설계 단계에서 명시해둔 것.

## HAVING과 서브쿼리

| | 언제 필터링하나 | 예시 |
| --- | --- | --- |
| WHERE | GROUP BY 하기 전, 개별 행 기준 | 날짜가 특정 범위인 행만 |
| HAVING | GROUP BY 후, 집계된 결과 기준 | 그룹별 합계가 N 이상인 그룹만 |

**서브쿼리**: SELECT 안에 또 다른 SELECT를 넣어, 먼저 조건에 맞는 ID 목록을 구한 다음, 그 목록을 바깥 쿼리의 필터로 쓰는 방식. 서브쿼리 안의 WHERE는 서브쿼리 자체에만 적용되므로, 바깥 쿼리에도 같은 조건이 필요하면 따로 다시 써야 한다.

## 자주 쓰는 함수 모음

| 함수 | 하는 일 | 주의 |
| --- | --- | --- |
| `ROUND(값, n)` | 소수점 n자리까지 반올림 | 말미의 0은 삭제됨 (6.00 → 6) |
| `FORMAT(값, n)` | 반올림 + 소수점 n자리를 항상 유지 | 0으로 패딩함 (6 → 6.00) — 똑같아 보여도 출력이 다름 |
| `CONCAT(a, b, ...)` | 문자열 이어붙이기 | 단위(km 등) 붙일 때 활용 |
| `MONTH(날짜열)` | 날짜에서 월만 추출 | `YEAR()`, `DAY()`도 동일한 패턴 |

**ROUND vs FORMAT 혼동 기준**: 문제의 예상 출력에 말미 0이 있는지 없는지를 먼저 확인하고 고를 것. 헷갈리면 "코드 실행"(채점에 안 들어감)으로 예상출력과 직접 비교해본다.

## 같은 값을 여러 컬럼에서 찾기 — OR vs IN

| 상황 | 쓰는 것 |
| --- | --- |
| 한 컬럼이 여러 값 중 하나인지 | `WHERE 열 IN (값1, 값2)` |
| 한 값이 여러 컬럼 중 아무 데나 있는지 | `WHERE 열1 = 값 OR 열2 = 값 OR 열3 = 값` |

방향이 반대라는 걸 헷갈리지 말 것 — IN은 "컬럼 하나, 값 여러 개", 이번 건 "값 하나, 컬럼 여러 개".

## GROUP BY 여러 컬럼 + HAVING — 중복/재구매 탐지 패턴

`GROUP BY 컬럼A, 컬럼B`처럼 컬럼을 두 개 이상 넣으면 "두 값의 조합"이 같은 행끼리 묶인다. `HAVING COUNT(*) > 1`을 붙이면 그 조합이 2번 이상 등장한 것 = 중복/재구매를 찾을 수 있다.

회계 실무로 치면: `GROUP BY 거래처, 금액 HAVING COUNT(*) > 1`로 같은 거래처+같은 금액이 중복 결제된 건을 찾는 것과 같은 원리.

## 자기 자신을 참조하는 JOIN (계층구조 조회)

부모-자식처럼 같은 테이블 안에서 관계가 있는 데이터(조직도, 카테고리 트리 등)를 다룰 때, 관계를 담은 테이블(예: `ITEM_TREE`)에는 ID만 있고 실제 속성(이름·등급 등)이 없는 경우가 많다. 이럴 땐 속성 테이블(`ITEM_INFO`)을 **서로 다른 별칭으로 두 번 JOIN**한다 — 하나는 "부모 쪽 조건 확인용", 하나는 "자식 쪽 결과 출력용".

```sql
FROM ITEM_TREE T
JOIN ITEM_INFO P ON T.PARENT_ITEM_ID = P.ITEM_ID   -- 부모 역할
JOIN ITEM_INFO C ON T.ITEM_ID = C.ITEM_ID           -- 자식 역할
```

**조건 확인만 필요하고 결과에 안 낼 거면** JOIN 대신 서브쿼리/EXISTS로 대체 가능 — 둘 다 결과는 같고, "출력에 그 역할의 컬럼이 실제로 필요한가"로 선택하면 된다.

## 흔한 실수 노트

- **ORDER BY에 원본 컬럼 쓰기**: `GROUP BY` 뒤에 `ORDER BY F.TOTAL_ORDER`처럼 집계되기 전의 원본 열을 써서 우연히 맞았던 경험. 안전하게는 집계함수의 별명(`ORDER BY TOTAL_ORDER`)을 써야 함.
- **ROUND → FORMAT으로 잘못 수정했다가 다시 ROUND로 복구**: "말미 0이 없어야 한다"는 반대 가설을 세우고 FORMAT으로 바꿨다가 실패. "코드 실행" 결과를 예상출력과 직접 비교해서 원인을 찾음 — 추측만으로 고치기 전에 실제 출력을 먼저 확인하는 가치.
